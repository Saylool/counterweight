# V5 autonomous keeper

Start only after the v5 owner lifecycle has been reconciled and no owner order/withdrawal is in flight:

```bash
npx tsx apps/keeper/src/mainnet-v5.ts --i-understand-real-funds
```

For a read-only rehearsal add `--dry --cycles=1`. The CLI is pinned to `cw5.haxheton.near`, `keeper4.haxheton.near`, `counterweight-mainnet-v5`, and the SHA256/base58 code hash of the local v5 WASM (also checked against SHA256SUMS.v5). Mainnet v4 keeper behavior remains commands-only. Runtime signing uses the existing near-cli OS keychain; implementation/tests never accessed keys or submitted transactions.

The loop polls public NEAR/Hyperliquid risk data every 30 seconds, heartbeats every 600 seconds using 5 Tgas, and signs/reconciles a reduce-only IOC when headroom falls below policy requirements. It never opens, supplies owner margin attestations, sells spot, or withdraws. Opening remains owner-attested. A configured oracle is refreshed with 40 Tgas before every reduction candidate and on ten-minute heartbeat intervals; a fresh callback is required (the keeper conservatively limits age to 60 seconds). With the verified unavailable Pyth configuration (`account_id:null`), refresh is skipped and fallback marks must meet v5's on-chain corridor/25bps anchor view; the expected receipt price matches the on-chain downward-quantized maximum margin-loss cap. Large market moves can block fallback exits, and tight IOC limits may remain unfilled. This does not authenticate caller market data.

Each reduction requests 285 Tgas. Before sends the loop reads the keeper's liquid balance, current gas price and protocol minimum gas purchase price. It retains 0.35 NEAR and budgets 110% of `max(2*live gas price, protocol minimum, 1e9)` times gas. At the 1e9 floor a close requires 0.6635 NEAR available after storage; 0.69 NEAR permits it. Heartbeats cost far less than blanket 285 Tgas calls. Every cycle requires the full close reserve before even sending a heartbeat. A low balance stops the loop for replenishment; repeated reads are free. The NEAR clock guard compares the read-start time against an optimistic block (3 seconds); observed timestamps are clamped to chain time.

Public RPC defaults to `https://rpc.mainnet.fastnear.com`, accepts `NEAR_MAINNET_RPC`, and falls back to `https://rpc.mainnet.near.org` with bounded read retries. Send functions are never retried. A durable control journal is claimed before heartbeat/oracle sends; any uncertain outcome blocks further mutations and stops. The existing durable signature/relay journals prevent re-signing or re-relaying uncertain orders. Logs and journals use `reports/keeper-mainnet-v5/`; protected v4 evidence and `reports/keeper-run/` remain untouched. A stuck order withholds heartbeat after half the policy timeout so public deleverage can recover. Stop with Ctrl-C/SIGTERM; inspect uncertain journals and finalized receipts before restarting. Do not run this loop concurrently with owner lifecycle signing steps, because they use separate journals; stop it first and reconcile any in-flight order.

Validation: 60 keeper tests passed (51 existing, 9 new) covering v5 consent/fixed identities, gas/protocol/clock guard, forged fallback, stale configured oracle, uncertain-send no-retry, low-balance loop stop, ten-minute heartbeat, oracle-before-reduction, bytecode pin, and capped reduce-only receipt expectations. `npx tsc --noEmit` passed. The loop itself was not started on mainnet during engineering.

The direct Chain Signatures derivation helper also has bounded transient-only mainnet public-read retries and endpoint failover. It preserves identical query bytes and pinned block hashes; permanent RPC/ABI/schema/block mismatches fail immediately, while testnet keeps its original single attempt. Eight focused retry tests plus lifecycle/keeper suites passed (90 tests together); TypeScript checked successfully. The existing 60-second L1 proof guard, five-second urgent reconciliation schedule, exclusive relay claim, and durable active-order journal remain intact.
